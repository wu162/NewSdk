# 完整 Upheaval：新编译器与老 SDK 的速度、缓存和恢复

测量已完成：每个正式场景在两台独立Windows VM配对重复，整套共12个VM测量作业、12个正式场景、92对计时。**新版关闭生成缓存时速度约为旧版1.20倍，完整直接出包约1.206倍；BC热建和单文件增量则是旧SDK明显更快。** 故障注入还发现旧版损坏缓存会传播错误字节、新版持久坏缓存未被修复；不将整轮写成正确性全部通过。

[持久计量JSON](UPHEAVAL_EXPANDED_RESULT.json)保存全部正式统计、430次原始构建观察、每进程CPU/峰值工作集、缓存计数、修改/故障证据、来源及独立runner身份。原单VM无缓存[10对结果](UPHEAVAL_BENCHMARK.md)保持独立来源，未混入本轮统计。生产编译器和SDK未修改。

## 无缓存与资产缓存

BC指每资产编译缓存，SC指会话缓存。两侧缓存分别存储；冷建清除生成缓存，热建保留确认缓存但创建新进程、重新链接。每VM5对，合计10对。这里的“冷”不是冷磁盘/冷操作系统页缓存；OS文件缓存已经预热。

| 完整MOD编译/链接 | 正式配对数 | 旧秒 | 新秒 | 旧/新比 | 配对95%区间 |
| --- | ---: | ---: | ---: | ---: | --- |
| 关闭生成缓存 | 10 | 82.342 | 68.594 | 1.2004 | 1.1957–1.2055 |
| BC首次冷建 | 10 | 83.804 | 88.947 | 0.9422 | 0.9392–0.9455 |
| BC无修改热建 | 10 | 24.149 | 45.804 | 0.5272 | 0.5247–0.5304 |

旧/新比大于1表示新版较快。新版无缓存耗时降低16.7%；BC冷建比旧版多约6.1%，热建为旧版约1.90倍耗时。与各自同VM的无缓存样本相比，老版BC热建加速3.410倍，新版1.498倍；新版首次填充BC缓存比关闭缓存多约29.7%耗时。

## 缺失、损坏与失败恢复

固定环境补测在每次破坏前证明对应命名空间实际命中。每种情况、每侧、每VM观察一次；不对拒绝或错误产物计算速度比。

| 注入 | 老SDK | 新版 |
| --- | --- | --- |
| 删除最大缓存载荷 | 正确重建输出，缺失文件重新出现 | 拒用该缓存、重新编译，输出正确；持久条目仍缺失 |
| 翻转最大缓存载荷末字节 | 返回成功但输出字节错误，两VM均复现 | 拒用该缓存、重新编译，输出正确；持久坏字节仍保留 |
| 无效根XML | 明确失败，确认缓存未变 | 明确失败，确认缓存与既有发布产物均未变 |
| 恢复健康备份/合法XML后重试 | 全部输出正确 | 全部输出正确，健康缓存恢复真实命中 |

新侧缺失/破损构建前后缓存目录哈希完全相同，因此“本次输出正确”不等于“持久缓存已修好”。缺失回退构建两VM为97.095/98.196秒，破损为97.037/98.702秒；恢复健康备份后的新侧重试约51～53秒。每VM仅一次观察，无性能区间；复制备份成本在构建计时外，这不是清空缓存后的修复耗时（空缓存重建另见BC冷建）。

旧侧被破坏的是最大Texture `.asset`，新侧为其实际支持的最大BC载荷，**并非同一资源类型**；新版Texture BC本就未启用，不能声称验证了新版Texture缓存完整性。这里只证明选定载荷和故障的行为，没有游戏运行验证。旧错误输出违反本基准字节门槛，因此原运行和恢复补测保留失败终态，报告JSON明确 `measurementComplete=true`、`allCorrectnessGatesPassed=false`。

## 输入、计时和统计方法

- 固定历史SDK提交`bacfc69fc3e71c8116d1f22b933b8b6173170ecf`的完整Upheaval tree `5551fc26a6f96b62613443e0d0fa2958c14cbce0`：2723文件、300900885字节，194个随MOD提供的`.asset`输入全部保留，区别于样本生成的BC/SC缓存。未精简引用或替换为小样例。
- 五入口为Mod.xml、三个APT及MapMetaData_Global.xml；同SDK/Schema/资源搜索路径、Win32、pc/ss/slowclean=true。原版逐入口启动BAB，新版一次CLI处理全部入口。未修改完整MOD的基线为1311文件、77873601字节，未修改正式样本通过同一身份门槛；变更样本使用独立无缓存oracle。
- 旧工具复制到临时目录，仅配置明确的绝对搜索路径及CLR4/legacy-v2激活策略；原EXE/DLL不改。新版复用.NET4.8正式Release包。不据此推断旧CLR2机器表现。
- 使用perf_counter，含进程创建/退出、正常日志/事务及链接。编译组旧侧累加各原生调用的wall time；出包组计完整流水线wall time（含调度和文件动作）。输入准备、框架重置/备份复制、最终哈希检查不计时。OS缓存预热，每次进程全新，不称为热JIT。
- 交替旧→新/新→旧，另一VM反转首引擎；BC冷热在同引擎块内依次执行，无缓存在块前/后轮换。预热和prime不进正式统计，不删离群值。每VM样本数有限，各VM数据全部保留。
- 以旧/新算术均值比报告效果，VM内配对、按VM分层bootstrap，10000次、seed162，百分位95%区间。区间只反映所观察VM层内的重复噪声，不是所有机器/MOD的保证；独立runner_id不证明独立物理主机。同一行可比较，不跨不同VM场景做绝对时间相减。
- 方法参照[hyperfine](https://github.com/sharkdp/hyperfine)的预热、准备和重复计时，以及[Google Benchmark](https://github.com/google/benchmark/blob/main/docs/user_guide.md)的重复与聚合原则，直接测真实Windows构建命令。未做游戏内验收，AssetMerge不在范围内。

## 解码完整原始计量

持久JSON顶层直接保存统计、来源与验收状态；为避免大体积提交连接阻塞，430次完整构建记录使用无损XZ+base64存放在 `rawMeasurements`。解码后是完整schema-v1 JSON，含所有原始样本、配对和观察；原始UTF-8长度993408字节，SHA256 `cac8fed77882bd87abe44b326d52e259489a7294ccb849dcbccd25e5563be3b1`，未删减数据。下面的Python代码可验证并导出：

```python
import base64, lzma, hashlib, json
from pathlib import Path
result = json.loads(Path("UPHEAVAL_EXPANDED_RESULT.json").read_text(encoding="utf-8"))
archive = result["rawMeasurements"]
data = lzma.decompress(base64.b64decode(archive["xzBase64"]))
assert len(data) == archive["decodedBytes"]
assert hashlib.sha256(data).hexdigest() == archive["decodedSha256"]
Path("upheaval-expanded-decoded.json").write_bytes(data)
```
