# 热缓存慢于无缓存：执行方案

更新：2026-10-28。所属：[实施计划B组](CACHE_PARALLEL_PLAN.md#plan-b)；状态：[当前交接](../REFACTOR_RESUME.md)。Codex云端执行与Actions验收遵循 [EFFICIENCY](../EFFICIENCY.md)。

**当前任务是降低缓存的端到端额外开销；以下是待实现方案，不是新验收或收益声明。** 先完成下面第一批，再按结果推进第二批，不继续增加计时平台或扩大XML资格。

## 已知原因与收益边界

最新小mymod测量来源为binary `e86958de` / test `e5809d10` / run [40693590489](https://github.com/wu162/NewSdk/actions/runs/40693590489)：Release无缓存760ms、三热中位2217ms，热47hit/0miss/0backend，四输出原字节一致。首热盘点1360.599ms（含受控读1007.240ms、枚举271.533ms），私有恢复15.806ms、Key3.864ms。首热子阶段不是三热中位的分解，不可混合相减；子阶段嵌套，受控读也不等于纯SHA。

源码核对基于 `e5687cb4`：
- `CoreStreamCompiler.Compile` 的缓存分支在stream前后调用 `CaptureInputs`，无缓存路径不做这两次全根盘点；`CacheInputSnapshot.Capture` 每次遍历SDK/MOD/runtime，包括每文件打开及摘要读取/复用。
- `CacheInputLeaseSet` 已在同一compiler生命周期共享，最多512个文件，偏向保留大文件；命中仍新开当前路径并核对128位文件身份。MOD（含SDK内嵌MOD）和SDK/Additional保持鲜读。**不能把“新增build级租约”当优化，因为现有实现已经有。**
- 所以命中率已不是当前主要瓶颈。缓存节省的后端执行时间必须大于输入保护、查找和恢复的新增成本才有净收益；廉价XML小MOD尤其难达到。历史Upheaval也有热缓存慢于无缓存并行的现象，但其二进制与此批不同，不据小MOD推断其阶段占比。

## 第一批：保持现有保护范围，减少元数据与重复读取成本

| 改动 | 实现入口与边界 | 验收要点 |
| --- | --- | --- |
| 合并目录信息获取 | 在 `CacheInputSnapshot.Inventory` 使用一次枚举取得可用属性，避免每条目重复属性查询；先核对目标.NET/Windows API及失败语义，仍按原ordinal顺序序列化 | reparse、目录替换、权限/消失、相邻前缀拒绝行为不退化；不能仅信任早先枚举属性 |
| 复用稳定文件的工作 | 沿用 `CacheInputLeaseSet`，共享同一build内规范化分类和已证明稳定的摘要；同一路径因重叠根重复出现时，只有连续租约及当前路径身份核验成立才复用，逻辑根条目与序列化身份保留 | MOD/Additional继续鲜读，租约外文件不凭路径/mtime/size复用；不能静默扩大512句柄上限 |
| 降低租约管理成本 | 仅在现有计量/定向检查确认有价值时，减少淘汰和最小长度维护的重复遍历；优先复用现有数据结构，不建预测器 | 容量、文件替换、身份API失败、部分获取失败及Dispose释放合同不变 |
| 分离可共享内容与stream描述 | `Capture` 中root内容、工具链摘要与task/options描述分别组织，共享只在字节版本证明有效时成立；`CoreStreamCompiler` 保留每个原检查时点 | 不将前一stream快照直接充当下一stream当前输入；工具/config/schema变化仍拒绝；旧session路径保持 |

完整覆盖/变化拒绝合同先保持，不能为了减少capture数量直接删stream尾扫描、跳过SDK其他目录或用MOD很小作为少读依据。无稳定证明的输入必须重读；第一批不能承诺消除所有首次全根成本。

## 第二批：有界并行必要读取，减少首次及不可复用输入的wall time

第一批若仍由受控读主导，直接在现有Capture内对**必须鲜读**的文件增加小型有界读取队列；先用1/2/4个reader作定向对照，生产上限由测量和资源预算选择，不随 `--jobs` 无界扩张。不增加产品子进程。

- 每个reader独占SHA对象、缓冲及只读拒写handle；不跨线程共享当前Capture的SHA实例。`CacheInputLeaseSet` 当前字典非线程安全，保持owner管理准入、复用、淘汰与计数，不能直接让多个reader调用现有 `Read`。
- 仅把必要鲜读派给worker，owner按确定的原路径顺序写入摘要和工具身份；队列同时约束在途文件、打开句柄、读取缓冲和待归并结果，不能先把全根payload读进内存。
- 属性/身份和摘要必须对应实际打开的文件；保留已有路径边界及变化检查。共享拒写失败、替换、取消或读取异常时停止派发、安全汇合并释放所有句柄，再走原失败/回滚路径。
- 读取并行不等于后端并行，分别报告；不得把worker的累计耗时加总成wall time。磁盘争用或小文件开销使并行无收益时保留串行，不宣称普遍加速。

## 后续结构优化的条件与停止线

保持全根保护就仍有首次扫描的成本下限，不能承诺仅靠上述两批让所有小MOD热缓存都快于无缓存。若两批后开销仍明显，依据新计量决定下一项：
- 仍是输入保护：研究“实际读取内容 + resolver查找/不存在/覆盖决策 + 工具/config/schema”的完整闭包。必须覆盖前端与native读取、目录成员及路径优先级，冻结/租约保证hash与消费一致，发布前验证仍有效；未知读取保持原路径。仅ReferencedFiles清单不够。
- **用读取闭包替换全根扫描会改变“任意根成员变化即拒绝”的现有行为，不属于本节可直接实施项。** 必须另列行为变化、覆盖证明与迁移验收，经用户确认后再改合同；此前继续保留全根保护，不暗中删除未证明无关的输入。
- 只有新证据显示前端/链接占主导，再按[计划第9节](CACHE_PARALLEL_PLAN.md#plan-performance)推进其复用；不先构建持久语义图、常驻守护进程、USN/watcher或跨执行mtime摘要缓存。
- 不新增自动关闭缓存来掩盖回归；默认仍关闭，显式开启仍如实报告成本。若最终仅适合昂贵后端或大型MOD，明确适用范围。

## 集中验收与“解决”的判定

1. 复用现有缓存/payload/Core/SDK测试入口，第一批与第二批分别成组提交和验证，生产变化集中重建；文档本身不构建。保留等长mtime修改、根/文件替换、新增覆盖资源、删除/换类型、嵌套MOD、Additional、身份失败、容量/租约释放、取消/异常、发布/缓存回滚、旧session及严格输出对照。
2. 用同runner、同输入/SDK、同配置、同jobs和相同输出布局，比较旧/新二进制的无缓存、空动作缓存、热缓存、单资产修改、Additional-only。工具实现变化会影响ActionKey，旧/新各自建store并预热，不能共用不匹配的热store。无缓存与热缓存交替顺序至少3对，保存中位数、范围及原始报告；OS缓存条件显式记录。
3. 复用现有阶段字段，必要时仅补fresh-read/reuse/open计数及读取最大并发；比较端到端、盘点、hash/read/copy、句柄/内存和真实后端调用。小mymod先验收；生产批次稳定后在专用分支低频复测完整Upheaval，保留串行/并行的同jobs缓存对照与原字节一致。
4. “减少开销”与“解决倒挂”分开：前者需可比的新旧热运行下降且正确性通过；后者需指定样例中热运行稳定快于同配置无缓存，差异超过本轮波动，并报告冷缓存/单改代价。只有读取量减少、单次最快或零后端调用均不算解决。未达到就写明仍慢多少、剩余主导阶段，不换口径报成功。
