# 热缓存编辑优化：现状与下一轮

参考用户提供的 `NewSdk_hot_cache_session_summary_2026-10-30.md`（研究版本 `5c1843ae`），本页只保留当前结论、待办和验收要求。当前成果为 `perf/compiler-cold-hot-cache` / [PR #38](https://github.com/wu162/NewSdk/pull/38)，已验收生产源码 `e2dba3c3`；续接时先核对远程头及 PR 状态。完整计量与原始证据见[本轮报告](COMPILER_COLD_HOT_OPTIMIZATION.md)，源码细节见[深入分析](COMPILER_CACHE_SOURCE_ANALYSIS.md)。

## 当前做到哪里

**文档前端按整份 XML 重处理，后端按资产决定是否编译。下一轮重点是减少不必要的前端工作。**

| 研究指出的问题 | 本轮结果 | 尚未解决 |
| --- | --- | --- |
| 局部编辑仍让整文档参与表达式、继承、XSD、哈希和引用处理 | 已共享编译后的 Schema、缓冲 XML 哈希、缓存 Schema 分类 | 没有实现实例级前端复用，未改兄弟仍参与处理 |
| 多流重复读取会话 | 已复用同次请求内成功保存的 SessionCache，精简查询/冗余索引 | 每流仍重置瞬态状态，没有跨流保留安全父 DOM |
| instance Include 将整个父文件登记为依赖 | 已核对源码并定向验证 | 父无关兄弟修改仍可能让子文档重解析 |
| 为继承取得父 XML 可触发 PrevalidatedLoad | 已降低其共同哈希、Schema 分类成本 | 仍可能重做父文档前端 |
| Define 与会话元数据失效应分层解释 | 已验证实际使用/未使用 Define、只丢会话元数据 | UsedDefines 按文档实际使用值判定是已有机制，不算本轮新增优化 |

完整 MOD 无修改纯热态耗时下降 **25.63%**，扩容下降 **34.71%**；这些数字不能代表修改后构建的收益。扩容正式样本完成，追加诊断超时，整组失败记录保留在本轮报告。六类增量诊断仅为每事件一次 detailed 配对，存在较慢样本。例如，大文档单资产修改为635.87→602.43ms，两边仍解析1份/编译1个；父无关兄弟修改两边仍解析2份/编译1个；未使用Define修改为545.42→547.13ms。它们验证失效和复用行为，不能证明稳定编辑加速。

## 下一轮优先级

### 1. 收窄 instance Include 的内容依赖

目标：父文件仅改无关兄弟时，仍处理和验证父文档，但子文档尽量复用；实际继承内容变化时，受影响后代仍正确失效。

- 从 `GatherUnvalidatedIncludes`、`Reinitialize`、`ProcessIncludedDocuments` 和继承缓存检查入手，区分依赖来源、解析后的路径身份和实际使用的父实例闭包。当前 `DependentFiles` 是无来源类别的路径列表，同一路径还可能来自 XInclude/素材引用，不能直接删除父文件哈希检查。
- 父文档处理完成后，再依据实际继承结果判断子文档是否重载。身份必须覆盖父 Define、XInclude、继承链、外部文件绑定及搜索根变化；父原始文本或单独的 `PrevalidationXmlHash` 不足以替代完整依赖。
- 先确定旧会话如何读取、迁移或安全回退。无来源信息的旧记录不得被当成已证明可复用；保留父输入的非法 XSD、重复声明及缺失/循环引用的拒绝行为。
- 验收重点：成对比较“父有效字段修改”和“父无关兄弟修改”，用子文档实际重解析次数及阶段耗时证明范围收窄，后端编译数不能代替该证据。

### 2. 复用供继承读取的父实例快照

目标：父实例已经成功处理且依赖未变时，减少为取得继承节点再次执行整文档前端。先量化 `cache.reload.inheritanceTarget` 次数及成本，再优先做请求内、按需、只读快照。

- 固定快照所处的处理阶段，保持默认属性、PSVI/Schema 类型信息及继承结果；验证 `CloneNode` 的实际行为，不能假定复制节点就等价。
- 复用身份覆盖 Schema、父输入和依赖、实际 Define 值、配置。只发布成功完成的快照，失败/取消不提交；避免复用带引用索引、CDATA路径和所属文档状态的 `InstanceDeclaration._Current`。
- 保留会话初始化和跨流状态清理。请求内方案先避免跨进程持久化/缓存格式扩展；覆盖多子文档、跨流及父依赖变化，记录实际减少的继承重载与内存开销。

### 3. 降低引用处理成本，再评估实例级前端复用

最新独立完整 MOD detailed 诊断：引用处理约 **5.89s**、实际 XSD约 **5.96s**、实例哈希约 **0.91s**。这是完整 MOD 的阶段计时，不是一次编辑的耗时，也不是可全部消除的收益。下一步优先拆解 XPath/SchemaInfo 遍历、字符串哈希登记、显式强引用类型对判断和文件路径解析，减少确定的重复工作；不继续把哈希微调列为首要任务。

更细的实例级表达式/Define读集合和前端复用属于后续结构性工作：需处理继承、默认值、引用重写及文档唯一性约束。UsedDefines 已有文档级精确使用集合；如研究旧项残留，应构造多代变更复现，成功完成后才提交新集合。纯热态的大规模排序另见[源码分析](COMPILER_CACHE_SOURCE_ANALYSIS.md)，不混入日常编辑收益。

## 验收与执行

- 先用现有六类场景定位和验证：大文档单资产、有效继承字段、父无关兄弟、已使用/未使用Define、仅丢会话元数据。新失效逻辑补齐增删/移动、搜索根遮蔽、XInclude、继承链及失败后重试的相关边界；素材重处理补真实WAV/DDS/W3X样例，避免只以Armor代表所有类型。
- 核心编辑场景至少做3组同机同输入、固定jobs的 `--performance off` 基线/候选配对；detailed用于归因，单独报告。保留全部样本和较慢项；延续等长、同mtime修改。纯热态、修改后、元数据重建、真正无缓存分别统计。
- 记录 `xmlParse`、失效原因、`cache.reload.inheritanceTarget`、引用/校验阶段和 `instanceCompile`/插件类型。每代基线/候选实际发布原字节一致，再热应0解析/0编译；新粒度优化必须证明工作量减少，耗时只改善但范围不变需如实说明。
- 保留完整XSD约束和非法输入拒绝；快照身份、依赖及成功验证证据成立时，可复用已有验证结果。保留实际依赖失效和适用的原SDK/Core/CLI/取消回归，整组实现后集中验证；生产输入未变的有效证据可复用。不恢复全树SHA身份扫描或BIG/SKUDEF包缓存，不增加无依据的热路径重复检查。
- 总时限2小时，源码分析、实现和独立验证并行，等待Actions时推进独立工作；优先交付一组可验证改动，再依次推进。第1/2项如有明确阻塞或无法在时限内完成验收，记录阻塞并转做第3项已证实的重复工作。仅有原型/未测的项保持待办。禁止强推；合并须用户明确批准。
