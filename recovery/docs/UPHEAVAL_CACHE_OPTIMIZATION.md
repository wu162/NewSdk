# Upheaval 缓存路径优化与三版本实测

本轮减少重复扫描和文件搬运，保留发布前的完整内容校验、损坏缓存拒绝、路径边界与事务回滚。性能结论来自同机三版本重复计量，不用旧机器的历史均值相减。

生产验收：[run 40788966635](https://github.com/wu162/NewSdk/actions/runs/40788966635)；正式计量：[run 40789589030](https://github.com/wu162/NewSdk/actions/runs/40789589030)；[PR #18](https://github.com/wu162/NewSdk/pull/18) 未合入。

## 实际修改

1. 输入清单从每个流前后各扫描一次，改为整个构建开始一次、全部流结束且 provider 释放后一次。每流请求/计划仍单独参与缓存键，发布前统一拒绝内容变化。变化会在整构建末尾拒绝，而非逐流立即拒绝；已确认输出和缓存仍受回滚保护。Upheaval 的五个流从 10 遍降到 2 遍，即 174430 次文件内容哈希降到 34886 次；不依赖 mtime 判定内容不变。单次扫描复用 SHA256 实例，避免逐文件创建算法对象。
2. 缓存恢复保留索引、路径、文件集合和长度检查，将负载 SHA256 合并到实际复制循环，移除复制前和复制后的重复读取。损坏负载先删除本轮部分恢复，再按未命中处理；不把错误字节交给 Core。
3. 已验证恢复且没有新增可缓存资产时，跳过候选缓存生成。完整热建的 base 流不再复制/哈希出一份最终会被丢弃的缓存；APT/maps 的空缓存路径仍保持原行为。

这是一组联合优化，没有分别消融每项改动，不能把总收益精确分摊到某个函数。

## 正确性与覆盖

- 新生产源码重新完成 Debug/Release 应用、Native/Core、真实 CLI、取消、BC 冷热/等长等时间失效/重试、Audio/W3X 负载、SC、输入根、BIG 和完整 mymod 回归，使用验收后的五文件 Release 包计量。
- 新增共享清单的内容变化/新增/重命名/任务隔离测试，以及最终校验失败和取消时保留上一代发布、最终校验仅一次的测试。原损坏缓存、pending、回滚等检查继续执行。
- 正式计量所有版本的完整 Upheaval 产物名称、长度、SHA256 必须与既有完整无缓存基准一致，包含 1291 个 CDATA，共 1311 文件、77873601 字节。108 份完整输出清单另已逐一核对一致。所有正式样本和预热样本均通过；没有用失败样本计算速度比。
- 两个新版热建均要求实际 1617 命中、0 未命中；老 SDK 热建要求 1734 条真实缓存复制记录。优化后 BC 每次必须记录 2 次完整输入扫描，热建 base 必须跳过候选提交。
- 没有开放 Texture BC，没有改变整个输入指纹导致的单文件失效粒度，也没有新增损坏 BC 持久存储自动修复。SC 的完整 Texture 限制继续保留。

## 方法与边界

固定完整历史 Upheaval：2723 文件，git tree `5551fc26a6f96b62613443e0d0fa2958c14cbce0`。每台 VM 一整组预热被排除，随后五组正式测量；每组有三个版本及无缓存/冷缓存/热缓存三种场景。共 108 次完整构建观察，其中 90 次正式观察组成 30 组三版本对照；预热 18 次全部保留。

三版本顺序使用六种排列，第二台 VM 更换起点；每个版本冷缓存后立即热建，无缓存的前后位置按组交替。进程每次重新启动；OS 文件缓存不清空且已预热，BC 冷缓存仅表示编译器原生资产缓存为空，不代表冷启动 OS 或热 JIT。

老 SDK 在临时配置中启用 CLR4/legacy-v2 activation 和相同绝对 SDK 搜索路径，EXE/DLL 未修改；不能把这里结果外推为 CLR2 对 CLR4 比较。本轮只比较完整 loose 编译/链接，未重测完整出包或增量场景的性能。

| --- | --- | ---: | --- |
| 1 | AMD64 Family 25 Model 17 Stepping 1, AuthenticAMD | 4 | 1000001934 |
| 2 | Intel64 Family 6 Model 207 Stepping 2, GenuineIntel | 4 | 1000001935 |

两台不同 hosted VM 以 GitHub runner ID 核验；不声称覆盖不同物理硬件。每台 VM 的绝对均值、分布、原始进程指标和所有配对均在持久计量文件中。
