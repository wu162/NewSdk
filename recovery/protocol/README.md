# Build information protocol 1.0 (P2)

`NewModCompiler plan --mod <directory> --sdk-root <directory> --out <directory>` discovers selected stream roots and writes UTF-8 `build.log`, `build.events.jsonl`, and `build-report.json`. `--events`, `--report`, and `--log` override their paths. Diagnostics use stderr. `--events -` is rejected pending verified native output isolation.

The standalone App entry has no asset backend and rejects `build` with `BACKEND_NOT_INTEGRATED` (exit 3). The unified production EXE integrates the experimental Win32 loose Core backend (caching disabled unless `/bc:true` is requested). A successful `plan` report states `PlanOnly` and `NoCompilationRequested`. Controlled App tests inject an executor which is not shipped in production; actual Core and CLI acceptance remain separate evidence.

The standalone net48 x86 App project is a validation entry. App sources have no dependency on a recovered business DLL and can be inputs to the unified module build. Build with `recovery/scripts/BuildApp.ps1`; test Debug and Release with `TestApp.ps1`. Both use VS Roslyn and the .NET Framework 4.8 reference assemblies, without downloading packages.

## Paths, parameters, and plan

`--mod` must be an existing directory, including SDK-external directories and names containing spaces or Unicode. `--sdk-root` is independent. `--out` or `/od` is required and may not overlap either source tree. Diagnostic files must be distinct and must not reside inside source trees. CLI paths are resolved once against the invocation directory; project sdk-root/out paths are relative to the MOD directory; the app does not change the current directory. `Data/Mod.xml` is required when base is explicitly selected. apt discovers `Data/AptUI/*.xml`; maps discovers `Data/AdditionalMaps/MapMetaData_*.xml`. Empty optional selections are recorded as `SkippedNoInputs`. Sorting and task IDs are deterministic and case-insensitive output collisions fail. The default plan explicitly reports `PlanKind: StreamDiscovery`. XML Include/reference closure belongs to Core within each stream; P2 does not pretend to resolve it or invent cross-stream dependencies. An optional `IDependencyPlanner` may supply an explicit stream dependency graph; the application deduplicates identical tasks, orders dependencies before consumers, and rejects cycles, missing inputs, unknown dependencies, or conflicting task/output identities.

`newmodcompiler.json` in the MOD root accepts profile, SDK/output paths, content/format, package identity, Additional/neutral flags, tp, jobs, and ss/pc/slowclean. Values use the existing scalar conversion (including numeric versions); boolean options accept booleans or true/false strings. Command-line options override project values; project values override defaults. Defaults are automatic input discovery (`auto`), `big` with Additional, and `Win32`. `--profile development` defaults to loose; explicit formats/selections retain their behavior. Automatic discovery without valid streams fails with PLAN_NO_INPUTS. `global-metadata` is the public selection name; legacy `maps` and internal maps task IDs/content/workspace names remain compatible. Unsupported formats and platforms fail during parsing. Repeated command-line aliases with conflicting values fail. Legacy `/art`, `/audio`, `/data`, `/dr`, schema, intermediate and cache paths retain their original strings and order for Core to resolve using its DataRoot/configuration semantics; they are not flattened into invocation-relative search paths. The production input-root candidate accepts `/dr`, `/data`, `/art`, and `/audio`: explicit search strings replace the corresponding MOD-prepended SDK defaults, retain semicolon order and the `*` document-relative wildcard, and are resolved by SettingsLoader after installing that stream’s DataRoot. A relative `/dr` is resolved from the SDK tools directory. These source changes require their own Windows/original-baseline acceptance. `/oix` and `/mr` are booleans, `/tl` is 0..9, and `/el` is 0..1, matching recovered Settings. Known legacy fields are preserved separately in `BuildRequest.Options`, with their source, for backend validation. In particular `/pc` is precompiled input, `/csc` is compression, and `/sc` and `/bc` are independent cache settings. Preservation is not a claim that the P2 skeleton implements cache or legacy output behavior. `/gui`, `/res`, `/pers`, `/mp`, `/poe`, `/sf`, and `/sh` are explicitly rejected. Unknown options fail.

`--jobs=N` uses the same option and project-preset pipeline. It accepts decimal positive integers up to 2147483647, defaults to 1, and is reported as `effectiveOptions.jobs` with its value and source. Invalid values return argument exit 2 (`CLI_RANGE`; empty/missing values use `CLI_VALUE`). The effective `/sc:true` with jobs greater than 1 returns `CORE_SESSION_PARALLEL_UNSUPPORTED` during parsing, before a build session or output channels are created. Project jobs are resolved before checking this restriction, so an explicit CLI jobs=1 can override a parallel project value. Jobs requests bounded backend concurrency; it does not change stream ordering or enable caches. Actual backend concurrency can be lower than requested jobs.

## Event and report contract

Every event includes schemaVersion, buildId, increasing sequence, ISO UTC timestamp, monotonic elapsedMs, eventType, and level. Optional streamId/stageId/diagnosticCode/message/payload provide context. A single synchronous dispatcher writes complete JSONL lines and flushes them. Consumers ignore unknown optional fields in a matching major protocol version. Breaking changes increment the major version.

Production cache reports add optional `executionEngine` (`AssetTasks.v1` or `LegacySession`), `cacheMode` (`ActionCache`, `Disabled`, or `SessionPackage`), `requestedJobs`, actual `backendCalls`, `maxBackendConcurrency`, and `actionHits`/`actionMisses`. These fields are additive protocol 1.0 fields; plan-only reports and injected test providers need not supply them. Actual backend calls and overlap must be measured from execution, rather than queue size or cache hits. Session reuse keeps its existing counters and is not reported as an action-cache hit. A running or unvalidated candidate report is not acceptance evidence.

A normal controlled session emits exactly one final `BuildFinished`. A forced process termination or native crash may omit it. Callers must verify the report buildId and status, final event, and process exit code together; missing or contradictory evidence cannot mean success. Report replacement uses a flushed same-directory temporary file and atomic rename/replace. Previous reports are removed before work starts. Required sink/report failures return 7; if an output channel is itself broken, a complete final event/report cannot be guaranteed. The remaining channels are attempted and never justify success on their own.

Compile tasks execute sequentially through one owned `IStreamCompiler` in one process. Each receives a new StreamContext and an isolated `.build/<buildId>/<content>/<stream>` directory. Returned artifacts must exist within that stream workspace; sizes and SHA-256 are recorded from actual files, rather than trusting a provider. The provider is disposed on every controlled path. Cancellation uses CancellationToken at safe boundaries, without Thread.Abort. On cancellation/failure only the current build workspace is removed, and its artifact list is cleared. Successful nonempty builds publish the exact artifact allowlist to `OutputRoot/published`, preserving stream-relative paths and replacing the previous generation as a directory. Unlisted staging files are excluded. `ArtifactProduced` records the compilation workspace path; the final report records the corresponding published path, with the same relative path, size and SHA-256. The current workspace is removed before final output-channel completion.

The publication transaction retains the previous generation until the report, terminal event and required sink closes succeed. Controlled report/terminal/close failures revoke the new generation and attempt to restore the old one; they return exit 7. `publicationStatus` is `PublishedDirectory` for accepted output, `NotPublished` when no generation was committed (including a successful empty optional selection), `RolledBack` after a committed generation was revoked, or `RollbackFailed` when restoration failed. `publicationDirectory` identifies the intended destination, and does not by itself claim that this build published anything. Empty optional selections preserve the previous generation and report an empty artifact list. A rollback failure records the retained backup location when available; callers must not treat that directory as accepted output. Obsolete backup cleanup after a successful commit is best effort and reports a retained directory on stderr. Process termination, power-loss recovery and cross-Windows-session concurrent publication are not implemented.

Cancellation is checked through the last safe boundary before writing the final report. Required report/event/sink finalization then completes without another cancellation check; an arriving cancellation cannot turn a completed terminal event into a different cancelled outcome. Required I/O failures can still invalidate an earlier success event, as described above. Diagnostic paths cannot overlap `.build` or `published`. This transaction is loose artifact publication; it does not imply cache, BIG packaging, complete P5/G3 or SDK acceptance.

Exit codes: 0 success (including plan only), 2 arguments/plan, 3 missing environment/backend, 4 compilation/input, 5 internal exception, 6 cancellation, 7 required diagnostic/report/output failure. Diagnostic codes are stable machine identifiers; callers must not parse translated message text. Parse errors before a valid output configuration are reported on stderr with a nonzero exit code; no session is claimed in that case.

Cache switches remain opt-in and default off. With `/sc:false`, production uses `AssetTasks.v1`: `/bc:false` disables persistent action-cache reads and writes, while `/bc:true` uses the versioned `.cache/action-cache-v1` store. Certified actions receive their own strong input identity and complete result contract. Uncertified types execute through the compatibility barrier and are not counted as action hits; Texture is in that category. Cache hits still pass verification and the same deterministic owner commit path as newly executed results. Jobs is scheduling context and does not enter the semantic action key. Full-root protection remains an input-change check, separate from per-action reuse identity. Complete cached results include their CDATA presence contract; damaged or incomplete entries are misses and repairs remain reversible.

With `/sc:true` and jobs=1, production retains the existing `LegacySession`/`SessionPackage` path, including its `/bc` combinations, full-root input guards and mixed-Texture refusal. Session reuse is reported separately from new action-cache reuse. Jobs greater than 1 with session caching is rejected rather than silently disabling the requested mode. For both cache paths, pending entries are excluded until publication and required report/event/sink completion succeed; failure or cancellation revokes this build's candidates. Source mode contracts and actual CI acceptance are separate: consult the current cache-parallel validation record for the verified backend/type matrix and run identity.

The input-root candidate exports `inputRoots` in the final report when a backend implements `IInputRootsCompiler`. It contains `dataRoot`, `schemaPath`, the ordered `dataPaths`, `artPaths`, and `audioPaths` arrays, and a `sources` object for DataRoot and the three arrays. Explicit values retain the matching effective-option source; defaults identify `sdk-root` or `mod-prepend+sdk-config`. This is the backend’s effective resolution contract, while `effectiveOptions` retains the original arguments. Plan-only sessions do not imply that Core resolved those roots. With `/bc:true`, an external effective root or resolved dependency is explicitly rejected until its contents are part of the cache namespace; `/bc:false` retains the ordinary resolver contract.

The `/bc` and input-root source candidates are under Windows integration verification. The source contract above is not a claim that complete P5/G3, session caching, every external-root combination or the full SDK has passed.
